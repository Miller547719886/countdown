# Apple 日历双向同步设计

## 意图

让“截点”的事项可以和用户选择的 Apple 日历保持双向同步：事项在截点中创建或编辑后，能出现在 Mac、iPhone、iPad 的日历中；用户在任一设备的日历中修改关联事件后，Mac 端截点下次收到日历变化时也能更新事项。

当前产品是 macOS 14+ 的本地优先 app，事项保存在 `ItemStore` 的 JSON 文件中，没有账号、服务器或 iOS 客户端。利用 EventKit 写入 iCloud 日历，系统本身负责跨设备传输，能在不引入后端的情况下满足三端联动。

## 目标

- 在设置中申请并显示 Apple 日历完整访问权限。
- 允许用户选择一个可写的 Apple 日历作为截点同步日历，并记住选择。
- 新建、编辑、完成、恢复、删除事项时，同步对应的日历事件。
- 监听 `EKEventStoreChangedNotification`，在外部日历事件被修改或删除后同步回截点。
- 只认领截点创建的事件，避免把用户已有的整本日历导入成任务。
- 在权限未授予、日历不可写、事件被外部删除或同步失败时，保留本地事项并给出可恢复的状态提示。
- 兼容当前 `CaptureItem` JSON；升级后旧事项可以继续使用，日历链接字段为空即可。

## 非目标

- 不实现 iPhone/iPad 版本的截点 app，不引入 CloudKit、账号体系或自建服务器。
- 不自动导入普通日历事件；不扫描用户所有日历建立任务。
- 不同步参与者、地点、重复规则、附件或日历提醒以外的 EventKit 元数据。
- 不把日历事件的结束时间当成第二个截止时间；截点只关心一个 deadline。
- 不改变现有截图、全局快捷键、通知和主窗口的视觉风格。

## 反目标（失败形态）

- 用户一打开功能就看到整本日历变成大量事项。
- 日历权限被拒绝后，本地事项无法新建或编辑。
- 自己写入日历触发的事件变化被再次写回，造成循环保存或标题不断叠加。
- 日历端删除一个事件导致本地事项被静默永久删除。
- 依赖 `eventIdentifier` 永久不变；iCloud 同步或更换日历后该 ID 可能改变。

## 约束

- Swift 5.10、SwiftUI/AppKit，最低 macOS 14；使用 EventKit 的 `requestFullAccessToEvents` 路径。
- `ItemStore` 仍是主线程隔离的本地领域存储；EventKit service 也在主 actor 协调，避免 UI 与 JSON 同时写入同一事项。
- Info.plist 需要声明日历用途说明；Package 需要链接 EventKit。
- EventKit 事件必须有结束时间，因此将 deadline 表示为从 deadline 开始、持续 1 分钟的非全天事件，并在事件开始时设置提醒。
- 日历跨设备是否可见取决于用户把目标日历放在 iCloud（本地日历不会跨设备）；设置界面必须明确这一点。

## 方案比较

1. **单向发布**：截点写入事件，日历只展示。实现最简单，但不能满足用户选择的双向同步。
2. **关联事件双向同步（采用）**：每个截点事项最多关联一个由截点创建的事件；两边都可以修改关联事件的标题和开始时间。只同步拥有明确标记的事件，保持数据边界清晰，不需要服务器。
3. **全量日历导入 + CloudKit**：将普通日历事件和截点事项统一到云端，并为每个平台做客户端。能覆盖更多场景，但超出当前 macOS 本地 app 的产品范围，且需要签名、账号、冲突和跨平台 UI 工程。

采用方案 2，因为它满足“双向同步”而不牺牲当前的本地优先和无账号约束；方案 1 功能不足，方案 3 成本和范围都过大。

## 领域模型与归属

### `CaptureItem`

在现有 Codable 模型上增加可选字段，旧 JSON 解码时使用 `nil`；为 `updatedAt` 和同步字段提供显式的向后兼容 `init(from:)`，不能依赖缺失键时的属性默认值：

- `updatedAt: Date`：本地最近一次事项内容/状态修改时间；旧记录回退到 `createdAt`。
- `calendarLink: CalendarLink?`：保存 `eventIdentifier`、`calendarItemExternalIdentifier`、`calendarIdentifier` 及最后一次同步时间。
- `calendarSyncState`：`unlinked`、`synced`、`needsAttention`，仅用于 UI 和重试，不改变本地事项是否可用。

所有本地变更都更新 `updatedAt`。事件标记使用自定义 URL（`jiedian://item/<UUID>`）并在 notes 中保留人类可读的同步说明；URL 是重新发现事件的主线索，EventKit ID 只是快速路径。若用户移动事件到别的日历或 iCloud 重新生成 ID，仍可通过标记找回。

### 同步范围

- 截点创建事项时创建关联事件；已有事项只有在用户开启同步并执行一次“同步现有事项”后才创建事件。
- 日历中新建但没有截点 URL 标记的事件不导入。
- 一个事项只允许一个关联事件；发现重复标记时保留最近修改的事件并把事项标为需要处理，不自动删除用户事件。

## 双向行为

### 截点 → 日历

- 新建事项：在选定日历创建事件，标题为事项文本，开始时间为 deadline，结束时间为 deadline + 1 分钟，添加 0 秒相对提醒和 URL 标记。
- 编辑文本或 deadline：按关联 ID/标记找到事件，更新标题和开始/结束时间；不覆盖用户在事件上填写的地点、参与者或其他备注内容，只维护自己的标记段。
- 完成事项：保留事件，不删除历史；在同步标记中写入完成状态，并在标题前显示一次 `✓ `。同步回截点时，只有标记状态或明确的 `✓ ` 才会把事项设为完成，避免普通文本包含勾号造成误判。
- 恢复事项：移除 `✓ ` 和完成标记，恢复事件标题与提醒。
- 删除事项：删除关联日历事件；若删除失败，本地删除仍完成，错误通过设置页的全局同步状态显示，不为已删除事项保留隐形记录。

### 日历 → 截点

- 收到 EventKit 变化通知后，重新获取关联事件；不依赖通知携带的旧对象。
- 事件标题变化（去除由截点维护的 `✓ ` 后）更新事项文本；开始时间变化更新 deadline，结束时间变化忽略。
- 事件的 URL 标记完成状态变化时更新 `completedAt`；事件被删除时，**默认只解除关联并保留本地事项**，标记为 `needsAttention`，避免日历端误删造成数据丢失。设置中提供“清理失联事项”由用户显式执行。
- 事件被移动到另一个可写日历时继续跟踪；若目标日历变为只读，只更新本地并提示无法回写。

### 冲突与循环

- 本地写入和外部通知都进入一个串行同步队列；写入期间设置 `isApplyingLocalChange`，忽略同一批次的自触发通知，稍后再做一次轻量 reconcile。
- 同一事项两端在离线期间都被修改时，按 `updatedAt` 与事件 `lastModifiedDate` 做最后写入胜出；若时间相同或无法确定，保留本地内容并标记 `needsAttention`，不静默覆盖。
- 同步失败不回滚本地事项；保存错误、权限错误和失联事件在设置里显示，提供“重试同步”和“重新选择日历”。

## 设置与用户流程

在现有设置页增加“Apple 日历同步”区块：

1. 显示权限状态；首次点击“允许访问日历”调用 macOS 14 的完整事件访问请求。
2. 授权后列出 `allowsContentModifications == true` 且支持事件的日历，显示账户/来源名称，并让用户选择一个目标日历。
3. 说明“只有 iCloud 日历会在 Mac、iPhone、iPad 间同步”；本地日历仍可用于测试，但不会跨设备。
4. 显示当前同步状态、最近同步时间、待处理数量，并提供“同步现有事项”“重试同步”“打开系统设置”。
5. 关闭同步只停止后续自动写入，不删除已经存在的日历事件；用户可在设置中显式解除全部关联并选择是否删除这些事件。

主界面和捕获面板不增加日历配置控件；保存后若同步失败，只在现有错误区域显示简短提示，事项仍可用。

## 同步生命周期

- `AppCoordinator.configure` 创建并保留一个 `CalendarSyncService`，订阅 EventKit 变化通知，读取权限和已保存日历配置。
- app 启动、授权完成、目标日历改变、ItemStore 加载完成后执行一次 reconcile。
- ItemStore 的 add/update/complete/restore/delete 通过 coordinator 进入同步服务；同步服务只在本地持久化成功后写日历。
- 外部事件通知触发 debounce（约 0.5 秒）后批量 reconcile，避免 iCloud 连续推送造成重复读写。
- 事件查询覆盖目标日历的合理时间窗口，并优先使用保存的 ID；URL 标记作为 ID 失效时的恢复路径。由于 EventKit 查询存在四年跨度限制，长期失联事件显示为需要处理，不无限扩大查询。

## 测试与验收

### 可自动验证

- `CalendarLink` Codable 对旧 JSON 向后兼容。
- 事件标记生成/解析、完成前缀清理、重复标记选择和冲突时间比较。
- 本地事项每种变更都产生正确的同步意图；权限拒绝、只读日历和事件不存在不会丢失本地数据。
- ItemStore 的完整现有检查继续通过；新增 release build 和 `git diff --check` 检查。

### 需要用户控制权限的验证

- 在隔离的 iCloud 测试日历中授权，确认 Mac 写入事件后 iPhone/iPad 能看到。
- 在另一台设备修改标题和时间，确认 Mac 端运行中的 app 收到变化并更新事项。
- 在日历端删除事件，确认事项保留且显示需要处理；显式清理后才删除本地记录。
- 不修改用户现有日历权限之外的设置，不在测试中自动删除非截点事件。

## 待用户确认的默认调用

本设计默认：只同步带截点标记的关联事件；日历端删除事件只解除关联并保留本地事项；完成状态用 `✓ ` 和标记字段表示；首次开启同步不自动创建事件，需用户点击“同步现有事项”。如果这些默认行为符合预期，设计即可进入实现计划；若你希望导入普通日历事件或让日历删除直接删除事项，需要在实现前调整范围。
